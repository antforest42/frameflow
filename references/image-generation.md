# 原生图片生成提示词结构

每个场景使用下面的结构，具体内容来自 `plan.json`：

```text
为中文知识类讲解视频生成一张横向简笔画插图。

画面只表达这个核心关系：{core_relation}。
主体与动作：{subjects_and_action}。
仅保留这些符号：{symbols}。

参考图1—2只用于理解黑色简化人物、少量彩色语义符号和关系构图；
参考图3是用户认可的输出样本，用于统一二维平面程度、人物粗细、纯色填充和画面密度；
最后一张参考图只用于匹配纯色背景。

默认方向：二维平面简笔画；黑色实心简化人物，少量{accent_colors}实心纯色强调；
主体大而清楚；横向关系构图；干净浅色纯色背景；不生成任何文字；
不添加无关环境；不复制参考图的具体构图。
保持扁平轮廓和纯色块，不主动生成渐变、材质纹理、体积光影、写实阴影、纵深空间或3D模型感；
不要把手掌、机器、墙体、植物、台阶或人物画成雕塑、玩具、写实物件或3D图标。
```

## 连续滚动任务池（禁止固定批次屏障）

图片生成前先完成整组任务包，并把确有连续性要求的任务写成显式依赖。调度状态分为 `ready`、`active`、`blocked`、`completed`；默认最大在途数为3。任务包落盘后立即发出最多3个 `ready` 任务，不得先写报告、发进度或打开预览；无外部阻塞时首图请求目标在10秒内开始。此后每当任一任务完成，都按以下顺序处理：

1. 只记录该图的完成时间、输出路径与调用状态。
2. 标记完成并解除以它为锚点的依赖。
3. 在 `active` 少于3时立即发出下一个 `ready` 任务，直到填满上限或暂时没有就绪任务。
4. 新任务已经补发后，把原生输出直接交给图片后处理流水线：归一化写入项目、必要单图初审、记录 `project_ready_utc`。

禁止采用“发3张 → 等3张全部完成 → 审核/复制/写报告 → 再发下一批”的固定批次流程。只要 `ready` 中仍有任务且 `active` 未到上限，就属于可避免空转。连续角色图可等待角色锚点，但不能挡住无依赖场景：例如图08是孟子角色锚点，图09、图10依赖图08；等待图08时仍应生成图11、图12等独立场景，图08返回后再将图09、图10放入 `ready`。

调度等价于：

```text
while completed_count < job_count:
    while active_count < 3 and ready is not empty:
        dispatch(ready.pop_front())
    finished = await first_completed(active)
    record_minimal_timing_and_path(finished)
    unlock_dependencies(finished)
    refill_active_slots()
    enqueue_postprocess(finished)
```

生成循环必须保持为长生命周期任务；面向用户的进度消息、下载或复制成图、打开预览和撰写耗时报告都不得中断它。图片后处理流水线以原生输出路径为输入，直接运行 `normalize_background.py` 写入 `images/<id>.png`，不先复制原图再覆盖；远程图片仍在生成时依次完成本地归一化和单图初审。清晰的不可用结果可以定点重试，但重试也是普通任务，仍受同一并发上限约束。服务端即使排队或实际串行，客户端也必须消除自己造成的等待，并如实记录服务端表现。

正常生产只生成一张最终项目图片联系表用于整组审核。原始输出已经由 `source_path` 保留追溯，不再常规生成原始图联系表；只有定位背景归一化或画风问题时才生成原始图诊断。

每个图片任务至少记录：

- `image_id`、`queued_utc`、`started_utc`、`completed_utc`、`project_ready_utc`、`elapsed_seconds`、`source_path`、`project_path`；
- 若有依赖，记录 `depends_on_image_ids` 与依赖解除时间；
- 整组记录 `task_package_ready_to_first_request_seconds`、首个请求至最后结果、`last_result_to_review_page_seconds`、`review_page_generation_seconds`、`avoidable_ready_idle_seconds`、`dependency_blocked_seconds` 和 `observed_max_active`。

`avoidable_ready_idle_seconds` 的目标值为0。多个请求互相重叠时，不得相加各自耗时后把结果当成墙钟耗时；没有相同模型、提示词、参考图、分辨率、审核和输出条件下的串行 A/B，就不得宣称确定的加速倍数。调度优化只改变发起时机，不改变原生图片模型、完整提示词、参考图、原始分辨率、审核标准或输出质量。

全部项目图片就绪并通过必要整组审核后，立即运行 `generate_review.py`。页面文件生成后先交付审核链接，再补充详细计时和诊断记录；详细耗时报告不得阻塞审核页。

## 成图判断：平面为原则，例外只在成图后判断

先检查整组是否仍然一眼属于同一套二维平面简笔画，再判断单张的语义和视觉完成度。结果优先不能覆盖整组画风原则，也不得把“局部例外可以保留”写回默认生成提示词。

- 渐变、透明、轻微透视、纸张卷曲或小范围立体结构，只有在局限于少量局部、主体仍是平面简笔画、与整组一致且确实增强表达时，才可作为局部例外保留。
- 体积光影、写实材质、3D手掌、机械臂、立体墙体、写实植物、雕塑感人物或纵深场景一旦主导整张图，属于风格错误；同类表现反复出现在一组图中，属于整组风格漂移，必须修正。
- 对象不必逐字照画；拼图、道路、屏障、容器等非字面隐喻，只要含义更贴切且保持平面画风，就可以保留。隐喻创意与3D风格是两个独立判断。
- 不得仅因一个局部有轻微渐变或透视，就抹掉一张整体成立的平面成图；拿不准的局部例外交给用户决定。
- 文件损坏、核心关系完全不成立、严重肢体/道具残缺、误导性的可读文字，以及明确的整张或整组3D画风漂移，都可以在用户审核前判为不可用。

例如，平面人物之间的一块半透明渐变屏障，或平面清单边缘的轻微卷曲，可以作为局部例外；棉花糖被转化为平面拼图或路径时，如果更好地表达未来、选择与自我建造，也应视为有效创意。整张图变成体积手掌、3D机器、写实植物或立体建筑，则不属于这种例外。

如果第一次生成存在明确且影响表达的局部问题，才编辑原图并只描述一个修改点，例如：

```text
保持人物、构图、颜色和其他元素完全不变，只把右侧人物的手臂补完整。
```

维护固定参考库时使用：

- `scripts/extract_reference_html.py`：从原始参考 HTML 提取图片和语义目录。
- `scripts/catalog_images.py`：为用户认可图片重建带 SHA-256 的目录。

目录中的 `count`、编号、文件名和 SHA-256 必须与实际图片一致；不一致时先确认当前图片是否为用户认可版本，再决定更新目录哈希或恢复图片。
